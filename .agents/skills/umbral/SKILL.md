Use the existing Umbrals checkout; the Godot project is at its root. Do not create a worktree unless requested. Read `AGENTS.md`, the game README and `docs/architecture.md`.
Read `docs/architecture-map.md` for current ownership and safe parallel handoff. One editor owns each file; shared facades, registry and baseline have one integrator. Agree interfaces before integration and freeze sources for full acceptance.

For roadmap and product-design conversations, also read `../umbral-design-interview/SKILL.md`. The user prefers grouped questions with options, an explicit recommendation, reference-game reasoning and tradeoffs; develop delegated details autonomously and record their status.

0. Run `python tools/harness.py preflight --fetch` before connected repository planning. Main means the current GitHub main. Compare remote commits/contracts and source evidence; preserve newer behavior while adapting stale refactors. Do not ask the user to choose an outdated local main as the default integration target.
1. Read `docs/roadmap.md`, choose the current milestone and one `Vxx-AREA-nn` slice, then state the intended behavior, observable outcome and acceptance criteria. For UI/feel work, read the game-local `.agents/skills/game-ui-ux/SKILL.md` and `.agents/skills/game-feel/SKILL.md`, then `docs/art-direction-v0.4.md` and `docs/ux-contracts.json`. The v0.3 art document is historical. Use the installed Godot, input, audio, card-game and asset skills when relevant.
2. Keep deterministic mechanics in `scripts/rules.gd`, authored species/forms, powers, items and encounters in `content/` through the `scripts/content.gd` facade, session persistence in `scripts/session/`, composition in `scripts/main.gd`, application coordination in `scripts/application/`, presentation in `scripts/ui/`. New species use `tools/umbrals.py author`; powers/items/encounters use `tools/content_authoring.py author` with ordered manifests. Item behavior belongs in its registered handler and parameter schema; new evolution is an explicit edge, never an ordinal. Run the catalog suite and legacy-save migration checks when these contracts change. Follow `docs/save-format.md` for ruleset compatibility. Screens own focus/input through the stack; HUD uses rule signals. Visual effects use separate RNG and bounded pools.
3. Preserve individual UID/passive across evolution. Capture creates another individual; replacement must require an explicit choice. Build decks from current owners and unlocked powers.
4. Preview must be pure: no randomness, rerolls or state mutations. Reject invalid/over-budget actions without spending a round.
5. Read `docs/harness.md` and `docs/architecture-guidelines.md`. Start with `plan --changed` and a focused suite/case/scenario; dependency resolution, isolated results and checked cache/resume are shared with CI. `bash tools/check.sh` runs every headless gate. This includes numerical trait/passive examples, seeded simulations, mutation checks and actual scene startup.
6. After fixes, freeze sources and run the full graph. For UI/input changes, run `python tools/iterate.py --label <name> --goal '<observable goal>' --baseline <previous-evidence>`, adding `--video` for motion changes. This already includes step 5, so do not run duplicate checks without a reason. Inspect menu, battle, capture, evolution, boss, replacement, large text and the resolution matrix. Open the generated review page and record specific observations and tradeoffs. A passing run is not visual approval; pixel difference is not a quality score. Preserve failed attempts.
7. To distribute, export the required targets and run `python tools/package.py`. Record asset provenance in the asset manifest/README. Validate the native Linux bundle with its graceful `--headless -- --smoke-exit` path, not an abrupt timed exit with audio running.
8. Report exact outcomes. Separate simulations, browser input, desktop export, real platform execution and subjective playtesting. Update the roadmap's iteration register with evidence, remaining criteria and the next slice. Refresh its visual map when scope or milestones change; do not bump the game version for planning or incomplete milestones. Documentation-only changes need proportionate document checks, not a duplicate gameplay run.

Keep generated evidence in ignored `test-results/` and immutable timestamped `artifacts/`; builds in ignored `builds/`. Read `docs/iteration-harness.md` for setup and review. Do not push or publish without user authorization.
